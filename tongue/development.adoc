== compiler stages

[source,text]
----
source text
  -> tokenisation and utf-16 spans
  -> parsing and source locations
  -> structural validation
  -> project loading, imports, and name lookup
  -> type, effect, coverage, shape, and fill checking
  -> evidence elaboration
  -> validated CoreProgram
  -> strict evaluation
----

keep these boundaries:

* tokenisation must not require parser state.
* parsing must not require type information.
* validation must not perform inference.
* only the type checker may construct a `CoreProgram`.
* evaluation must not repair a static error.
* editor analysis may approximate incomplete source, but compiler results remain authoritative.

module-local invariants belong in the module comments beside their
implementation. this guide explaineþ only relationships between modules.

== projects and imports

`Tung.Project` discovereþ local source bundles before checking. it resolveþ
relative brings from their owner, then platform-separated `TUNG_PATH` roots;
the embedded bookhoard is the final fallback. one written bring path resolving
to different canonical files is rejected.

the checker cacheþ each imported static context and elaborated core while it
walkeþ one acyclic graph. a `CoreProgram` carrieþ the elaborated root and its
flat imported-core map. evaluation resolveþ imports only from that checked map
and initialiseþ each shared module once.

== types, evidence, and evaluation

`Tung.Type` owneþ hindley-milner inference, effect rows, coverage integration,
shape requirements, fill selection, and dictionary elaboration. fill selection
is static: inheritance depth is considered first, then a type pattern may
outrank a broader pattern it strictly refines. equivalent imported candidates
are deduplicated before this comparison.

`Tung.Core` keepeþ its constructor private and rejecteþ unresolved evidence
or unelaborated fills. `Tung.Evaluate` runneþ checked core strictly. callable
values retain supplied arguments, so native work and effect operations run only
at saturation. handlers are deep and continuations remain reusable.

host metadata live in `Tung.Primitive` as one data-only catalogue shared by
checking and evaluation. add or change a host operation there before changing
the source binding in `_foreign.tung`.

== formatting and editor support

`Tung.Format` is the authoritative two-space source formatter for both cli and
editor. it is deliberately structural: it preserveþ comments and incomplete
source, remaineþ idempotent, and invoke neither parsing nor type checking.
typescript code under `vscode/server/format.ts` only converteþ lsp ranges.

the language server combine two paths. tolerant typescript analysis keepeþ
highlighting, navigation, completion, symbols, and folding available for
unfinished buffers. one versioned `tung --editor-session` process provideþ
authoritative diagnostics, inferred hover types, and formatting. cancelled or
stale responses must not enter editor state.

xref:../vscode/readme.adoc[`vscode/readme.adoc`] documenteþ editor setup,
features, and component checks.

== embedded library and generated metadata

`Tung.Embed` discovereþ the sibling `bookhoard/` tree at compile time. the
tracked `.bookhoard-membership` file containeþ paths and content fingerprints;
`make compiler-build` refresheþ it before cabal buildeþ. when cabal appeareþ
to reuse stale embedded sources, verify with a fresh `--builddir`.

`tool/language-names.tung` emiteþ the tracked editor keyword and primitive
table. run `make language-metadata`; do not edit the generated json. `writ/`
buildeþ ignored api html from shown declarations and attached doc comments.

== change and test boundaries

follow the owning stage first and then every consumer:

[cols="1,3"]
|===
| change
| required follow-up

| syntax or tokens
| parser, formatter, diagnostics, editor grammar and lexer, language guide, byspels, and tests

| type, effect, shape, or fill semantics
| type and evaluator regressions, bookhoard checking, and language guide

| runtime or host surface
| primitive catalogue, `_foreign.tung`, exact evaluator tests, and runner boundary

| public bookhoard api
| doc comments, membership, generated api tests, realistic byspel when useful

| editor behaviour
| tolerant and compiler-backed paths, typescript checks, and editor tests
|===

run narrow tests while iterating. before handoff, run `make compiler-test` for
compiler or bookhoard work, `make vscode-test` for editor or formatter work,
`make writ-test` for documentation generation, and `git diff --check`.

tests are part of the specification. keep successful and adversarial cases at
the stage which owneþ a rule, use exact evaluation results when deterministic,
and do not weaken static checking to preserve stale library code.

== reference model

tung adapteþ established work without copying its syntax:

* damas and milner ground let generalisation, instantiation, and unification.
* wadler and blott ground qualified polymorphism and explicit evidence.
* koka ground row-polymorphic effects and their interaction with let polymorphism.
* plotkin and pretnar ground algebraic handlers and resumptions.
* maranget ground usefulness and exhaustive pattern checking.

purescript informeþ strict functional module and class boundaries; lean and
mathlib inform lawful algebra and finite-collection distinctions. detailed
bookhoard comparisons live in
xref:../bookhoard/reference.adoc[`bookhoard/reference.adoc`].
